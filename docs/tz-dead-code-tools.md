# ТЗ: инструменты поиска мёртвого кода (BSL / конфигурации 1С)

Дата постановки: 12.10.2026. Источник — аудит возможностей на живом индексе
конфигурации ЗУП (≈1,8 ГБ, 29 679 файлов), стенд: бинарник code-index 1.8.5, код HEAD `4bd79eb`
= v1.8.6). Числа ниже — замеры того аудита, проверенные независимо (эмпирик, инвариантщик,
арбитр, мета-проверка), затем — аудит самого ТЗ.

## 1. Что происходит сейчас

Отдельного инструмента поиска мёртвого кода нет: ни один из 33 MCP-инструментов
(20 ядровых + 13 BSL) не отвечает на этот вопрос, и в README/docs/CHANGELOG такого
обещания нет. Ответ собирается только композицией `bsl_sql` + граф вызовов + таблицы
метаданных, и то частично.

## 2. Что требуется

### Требование 0 (форма ответа — общая для Требований 1 и 2)

Ответ обязан различать три разных факта, а не смешивать их:

- `results` — **только** «вызывающих не найдено» (кандидаты); это **не** доказательство
  мёртвости;
- `dynamic_possible[]` — процедуры, привязанные только строковым литералом
  (`ОписаниеОповещения` и т. п.);
- `not_checked[]` — кандидаты, у которых есть хотя бы одно **неразрешённое** ребро
  (`callee_proc_key IS NULL`), чей `callee_proc_name` совпадает с именем кандидата (для BSL —
  без учёта регистра); это вычислимо на существующих данных.

Рядом обязательны: `channels_applied[]` со счётчиком снятого по каждому каналу,
`channels_not_applied[]` (список каналов, которые не реализованы, — например программные
подписки), `unresolved_edges` (число рёбер с `callee_proc_key IS NULL`), `formula_version`,
`results_total`/`results_shown`. Число считается детерминированным **при фиксированных**
`channels_applied` и `formula_version`. Индекс, помеченный `stale`, ответа-числа не даёт:
возвращается `{"stale": true, "results": null, "hint": …}` — пустой массив `results` в этом
режиме **запрещён** и не должен быть отличим от «не найдено». Массив результатов не
обнуляется ни при каком бюджете (кроме `stale`-режима, где его нет вовсе); пагинация — как в
v0.49.0, с выдачей под ключом `results` (не `result`), чтобы не сталкиваться с сессионным
дедупом.

### Требование 1 (C1). Инструмент кандидатов с обязательным вычитанием точек входа

Новый BSL-инструмент (имя — на усмотрение реализации, далее `find_dead_code`).

1. Формула «мёртвый» фиксируется, версионируется (`formula_version`) и возвращается в ответе
   (см. Требование 0). Одно и то же определение обязано давать детерминированное число **при
   фиксированных `channels_applied` и `formula_version`** (сегодня 1 311 / 11 676 — режимы,
   а не число).
2. Точки входа вычитаются **из данных**, а не текстом. Каналы:
   - подписки: рёбра `proc_call_graph.call_type = 'subscription'` и таблица
     `event_subscriptions`;
   - события форм: рёбра `form_event` (а **не** `form_bindings`: она требует сегмент `/Forms/`
     в пути, `form_bindings.rs:118`, и теряет общие формы и внешние обработки/отчёты);
   - экспортные процедуры (`exported_procs`);
   - **реестр платформенных событий по типу модуля**, наполняемый на индексации. Типы модулей
     из `metadata_modules.module_type`: `ObjectModule` (994), `RecordSetModule` (388),
     `ManagerModule` (1634), `FormModule` (2747), `CommandModule` (362), `ValueManagerModule`
     (88), `Module` (1414);
   - **`CommandModule` → `ОбработкаКоманды`** — 362 процедуры на ZUP, не экспортные и без
     рёбер (`exported_procs` по этому имени — 0): без канала это 362 ложных «мёртвых»;
   - **обработчики команд формы** (`<Command><Action>` в Форме.xml, EDT `<action><handler>`) —
     сегодня парсер форм читает только `<Event>` и пропускает команды (`xml/forms.rs:226-258`;
     EDT — `edt_mdo.rs:932-1027`, doc-комментарий на `:937`; тест
     `form_handlers_extracted_actions_skipped` на `:1711-1726`), в `handlers_json` командных
     записей нет (23 677 записей, ключи только `event`/`handler`/`element`), поэтому канал
     требует сначала индексировать `kind = command_action`;
   - **перехваты расширений**: рёбра `call_type = 'extension_override'`
     (`index_extras/call_graph.rs:433-448`); на ZUP их нет (`override_type` = 0), но на
     CFE-конфигурациях это систематический ложный «мёртвый» и для перехватчика, и для базовой
     процедуры;
   - **не реализовано и помечается в `channels_not_applied`**: программные подписки
     (`ПодписатьсяНаСобытие`) — на ZUP 0 тел, но на других конфигурациях это точка входа без
     ребра.
3. Динамический слой: цели из строковых литералов (`ОписаниеОповещения`,
   `ПодключитьОбработчикОжидания`, `ФоновыеЗадания.Выполнить`) кладутся в индекс отдельным
   признаком; такие процедуры идут в `dynamic_possible[]`, а не в `results` и не в «живые».
   Детектор обязан исключать методные вызовы (перед `Выполнить` стоит `.` — это
   `Запрос.Выполнить()`/`ФоновыеЗадания.Выполнить(...)`, 9 039 в `calls`) — подстрочный
   `Выполнить(` как основа запрещён (даёт 6 799 FP против 48 реальных глобальных).
   Нелитеральные конструкции (`Выполнить(Правило.ПередОбработкой)`, `СтрШаблон`, склейка
   `"Префикс_" + Имя`, имя из реквизита) статически не материализуемы — про них допустима
   только пометка «возможен динамический вызов», привязка им не приписывается.
4. Регистронезависимость — **только для BSL** и как exact-first + fallback (точные совпадения
   ведут себя как сейчас, иначе регресс на Rust/Go/JS, где `GetUser` ≠ `getUser`). Тем же
   способом — в `qualified_callers` (сейчас байтовое `exported_procs.name = ?2`,
   `qualified_callers.rs:49`) и в резолвере `callee_proc_key`. Реализация — через колонку-ключ,
   а не `lower()` по колонке (иначе `calls` 904 502 строк теряет индекс). Канонические значения
   и UNIQUE-ключи (`metadata_objects.full_name` и родственные) не менять.
5. Адресация — к определению, а не к имени: пара (`files.path`, `functions.name`) в том же
   склеенном формате, что `proc_call_graph.callee_proc_key`
   (`call_graph.rs:717-719`). Проверка «есть вызывающие» идёт по `callee_proc_key` (у самого
   кандидата такого ребра нет по определению — иначе он не кандидат); для подписок и событий
   форм — по синтетическому ключу слоя (`Модуль.Метод` / `owner::form::handler`); процедуры
   вообще без рёбер (8 618 на ZUP) адресуются из `functions ⋈ files`.
6. Материализация и выдача: агрегат кандидатов перестраивается на индексации (иначе сырая
   воронка не проходит 8-секундный лимит: 14,1 с на приёмочном индексе), **атомарно**,
   привязан к `INDEX_DATA_VERSION` и `formula_version`; при `stale` число не отдаётся.
   Инкрементальная правка файла F пересчитывает кандидатность и динамические цели **самого F
   и всех `callee` из `direct_edge_files` этого файла** (старых и новых рёбер) — правка тела
   меняет именно сторону `callee`. Выдача — узкой
   проекцией (имя + путь) с пагинацией под ключом `results` (≈314 строк на страницу в форме
   `Value::Array`, ≈38 вызовов на 11 676 имён).

### Требование 2 (C2). Инструмент объектов без ссылок

1. Ссылки на макеты из кода должны индексироваться — тогда `Template` снимается вычитанием,
   а не исключением класса («просто исключать Template» несовместимо с приёмкой: нужен и
   снятый используемый шаблон, и оставшийся неиспользуемый). Канал строится из трёх
   источников:
   - **строковые пути метаданных** вида `<Коллекция>.<Объект>.<Макет>` — пара (владелец,
     макет) уже лежит строкой `member_path` у владельца в `metadata_code_usages` (это
     закрывает 190 из 2 427 шаблонов, включая оракул приёмки);
   - `ПолучитьМакет("Имя")` с резолвом владельца по модулю (654 вхождения / 252 имени,
     246 из них совпадают с именем какого-либо `Template`);
   - `ПолучитьОбщийМакет("Имя")` → `CommonTemplate.Имя` (48 тел; 57 из 64 имён общих
     макетов встречаются в телах).
2. `Subsystem`/`Language` — исключать или помечать «ссылочно не адресуемо» (332 из 347
   подсистем в принципе не бывают целями ссылок); пометка видна в ответе.
3. Объединять каналы (`data_links` входящие, `role_rights`, `metadata_code_usages`,
   новый канал макетов) и отдавать по каналам пометку, что именно проверено (Требование 0).

### Требование 3 (C3). Недостижимый код — новый слой данных

Отдельный этап. Минимум для приёмки: разметка блоков и ветвлений (`КонецЕсли`/`Исключение`/
`КонецПопытки`/циклы). Готового токенного API у парсера нет: `bsl-parse` отдаёт только
`AstFacts { declarations, calls, dots, news, parsed }` (`bsl-parse/src/lib.rs:32-44`), поэтому
блок-структура извлекается **новым выходом парсера** из tree-sitter-дерева. Детектор — код
после безусловного завершения блока (`Возврат`/`Прервать`/`Продолжить`/`ВызватьИсключение`).
Полный CFG в минимум не входит. Регулярные выражения по телу как основа **запрещены**.

### Требование 4 (C4). Неиспользуемые параметры/переменные — новый слой данных

Отдельный этап. Требуется: сбор локальных `Перем` с владельцем-процедурой и областью
видимости + индекс употреблений идентификаторов в теле. Параметры-приёмники
(`НаборЗаписей.Добавить`) и платформенные обязательные подписи (`Элемент`, `Команда`,
`Отказ`, `СтандартнаяОбработка`) не считать дефектом. LLM/enrichment не требуется.

## 3. Проверка приёмки

На живом сервере, репозиторий ZUP, дефолтный бюджет. Оракулы (кроме C3/C4) существуют в
данных уже сегодня:

1. C1: ответ детерминирован **при фиксированных `channels_applied`/`formula_version`** и
   содержит `channels_applied[]` со счётчиками; старого индекса (`stale`) ответа-числа нет.
2. C1: **точки входа отсутствуют в `results`** — с разбором, какой канал их снимает (иначе
   сломанный канал останется незамеченным):
   - **объектный обработчик**
     `Documents/АвансовыйПлатежИностранцаПоНДФЛ/Ext/ObjectModule.bsl` :: `ОбработкаПроведения` —
     не экспортный, рёбер 0 (по имени всего 175 объявлений, из них 4 экспортных: 2 в
     `CommonModules/*/Ext/Module.bsl`, 2 в `Documents/*/Ext/ManagerModule.bsl`; объектных
     не экспортных — 171). Это **негативный** оракул канала объектных событий.
   - **экспортная** `ПриЗаполненииОграниченияДоступа` (795 записей `exported_procs`, вызовов 0) —
     положительный контроль канала «экспорт».
   - **обработчик подписки** `АвтономнаяРаботаПроверитьВозможностьЗаписиОбщихДанных`
     (`event_subscriptions.id = 1`, `CommonModules/ОбменДаннымиВМоделиСервиса/Ext/Module.bsl:2706`)

## 4. Чего делать не надо

- Не поднимать дефолтный `max_response_bytes` под эти инструменты.
- Не объявлять «мёртвым» по «0 вызовов» без списка применённых каналов.
- Не решать C3/C4 регулярными выражениями по телу.
- Не менять смысл `sections=[]` и не трогать сессионный дедуп (`serve_dedup.rs`); вместо этого
  выдавать пагинацию под ключом `results`.
- Не перекладывать на `bsl_sql` как на основной путь: это «воспроизведение SQL», а не
  инструмент, и у него 8-секундный лимит.

## 5. Порядок выкатки

1. **Этап 1 (C2)** — на существующих данных: канал макетов (строковые пути `member_path`,
   `ПолучитьМакет`, `ПолучитьОбщийМакет`), пометка `Subsystem`/`Language`, объединение
   каналов. Дешёвый, закрывает систематическую ложь.
2. **Этап 2 (C1)** — реестр платформенных событий (включая `CommandModule` и обработчики
   команд формы), канал `extension_override`, регистронезависимость (BSL, fallback),
   детерминированная формула, динамический слой по литералам, **материализация агрегата**
   (атомарно, привязка к `INDEX_DATA_VERSION`/`formula_version`) и пагинация.
3. **Этап 3 (C3, C4)** — новый слой разбора (блоки и достижимость; локальные переменные с
   употреблениями).

Релизный цикл — как в `tz-search-results-omission.md`, не срезать: тесты workspace →
локальная сборка и smoke на живой базе → musl → раскатка на ВМ → федеративный smoke →
аудит секретов → коммит. Федеративные ноды обновлять синхронно: инструменты обслуживает
нода-владелец репозитория.
